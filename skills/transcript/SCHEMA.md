# SCHEMA - `docs_logical.json`

**File:** `projects/<project>/docs_logical.json`
**Purpose:** **single source of truth for processed archive data**. It is the only
artifact that consumers (e.g., `ui/main.html`) read. Generated by
`build_docs_logical.py` from raw sources - never edited by hand.

**Supported input formats:** `.jpg`, `.jpeg`, `.png` (images), `.pdf` (PDF documents)

## Compatibility rules (non-negotiable)

- **`schema_version`** identifies the version. Current: **`2.0`**.
- **Additive and backward-compatible:** new fields can be added; **never** remove
  or rename an existing field without incrementing major version and maintaining
  aliases. If in doubt, **ask** before changing.
- The consumer `main.html` depends on: `persons[]`,
  `relations[]`, `documents[].properties[]`,
  `documents[].transaction{buyer,seller,nature}`. These **must exist**.

## How it is generated (schema-agnostic pipeline)

```
documents-raw/*.jpg ──OCR genai (on demand only)──▶ metadata/*.json ─┐
                                                                     ├─▶ build_docs_logical.py ─▶ docs_logical.json
docs_logical_map.json  (document map) ────────────────┤
projects/<project>/GLOSSARIO.md        (normalization)─────────────┘
```

- **No script contains document data.** Image→logical document grouping,
  titles, types, and transactions live in **`docs_logical_map.json`** (data).
- The build always applies **GLOSSARIO.md** (reading corrections) to sources
  **in memory during generation** - it does **not** edit the `metadata/*.json` files. The same
  `projects/<project>/GLOSSARIO.md` is also provided as **reading support to GenAI**
  when generating/reinterpreting image JSON and the map (glossary applied at **2 points**).
- **Relations are normalized by logical document** (not by image): aggregated
  and deduplicated, maintaining links to original images in `source_images`/`sources`.

## `metadata/*.json` - OCR output (IMMUTABLE schema, never edit by hand)

> **Rule:** the `metadata/*.json` files are **OCR output** and are **never**
> edited by hand or by scripts with embedded data. They only change by **GenAI
> reprocessing (on explicit request)**, always with **this same schema**. Two modes:
>
> 1. **Visual re-OCR of the photo** - reads the image again and reproduces
>    `full_transcript` + fields.
> 2. **Interpretation of `full_transcript`** (without re-reading the photo) - GenAI
>    reads the already-transcribed text and (re)derives structured fields
>    (`entities`, `properties`, `persons`, `relations`), updating the same image JSON.
>
> OCR/reprocessing also runs for **new documents** in `documents-raw/`.
> The GLOSSARIO never rewrites these files; it is applied only during consolidation generation.

Fixed schema for each image JSON (1 per photo):

```json
{
  "image": "<name>.jpg",
  "document_type": "...",
  "document_date": "...",
  "location": "...",
  "full_transcript": "...",
  "entities": { "names": [], "dates": [], "places": [], "values": [] },
  "properties": [ { "description", "location", "article", "quota", "value", "confrontations": {"north","south","east","west"} } ],
  "persons": [
    {
      "name": "João",
      "roles": ["seller", "testator"],
      "variants": [
        {
          "name": "João da Silva",
          "source": "document_context",
          "confidence": "high",
          "reasoning": "Full name appears in opening clause"
        }
      ]
    }
  ],
  "relations": [
    {
      "from": "João",
      "to": "Maria",
      "relation": "vende a",
      "attribute": "sale",
      "label": "venda de propriedade",
      "source": "explicit",
      "inferedbyai": false,
      "inference_type": "explicit",
      "inference_confidence": "high",
      "seller": "João",
      "buyer": "Maria",
      "value": "100 réis",
      "date": "1850-05-15",
      "date_precision": "day",
      "date_original": "Fifteenth day of May"
    }
  ],
  "ocr_metadata": { "genai_model", "method", "ocr_confidence", "status", "notes" }
}
```

`entities`, `properties`, `persons`, `relations` are structured fields of the image JSON.
To review them **without re-reading the photo**, use GenAI reprocessing by
**interpretation of `full_transcript`** (on request) - never edit the file by hand.

## `docs_logical_map.json` - declarative map (DATA)

Schema read by the build (do not change without aligning the build):

```json
{
  "schema_version": "2.0",
  "logical_documents": [
    { "id": "DL01", "title": "...", "type": "...",
      "images": ["<name>.jpg", "<name>.pdf", ...] }
  ]
}
```

> **GenAI generation (allowed):** the `map.json` **can be generated/updated by
> GenAI** from the **`full_transcript`** and/or **`ocr_metadata.notes`** fields
> of the image JSON (which indicate document type, transactions, and grouping).
> The result **must comply with this schema** (fields `id/title/type/transaction`)
> for the build to consume it. Never invent; only what the transcriptions state.

## Relations (`attribute`)

**Canonical Relation Types (~22 total):**

**Genealogy (Core - 7 types):**
- `filiation` - parent-child relationship
- `marriage` - married couple (includes divorced/widowed)
- `kinship` - siblings, co-heirs
- `affinity` - in-laws
- `godparent` - godparent-godchild
- `descent` - computed from filiation chains (inferred)
- `inheritance` - heir to deceased

**Economic/Property (4 types):**
- `sale` - seller → buyer of property/goods
- `purchase` - buyer → seller (inverse of sale)
- `mortgage` - debtor → creditor (debt/pledge/loan)
- `debt` - general creditor-debtor relationship

**Succession/Wills (4 types):**
- `heir` - inheritor in will
- `legatee` - specific bequest recipient
- `executor` - will executor/administrator
- `testator` - person making will

**Legal/Judicial (5 types):**
- `guardian` - guardian of minor/ward
- `ward` - person under guardianship
- `procurator` - attorney-in-fact (power of attorney holder)
- `principal` - grantor of power of attorney
- `witness` - legal witness/attestor

**Legitimation/Recognition (2 types):**
- `legitimated` - person legitimized by parents
- `acknowledged` - person formally recognized as legitimate

**Fallback:**
- `other` - edge cases, context-specific, or unmapped relations

> **Transaction labels** (`label` field) should extract meaningful noun phrases from document text:
> - ✅ Good: "venda de propriedade", "hipoteca de terras em Cótimos"
> - ❌ Avoid: "vende a", "According to the deed...", empty strings

> **Transaction (`transaction`)** can be declared at the **image level** in `metadata/*.json` 
> as structured fields within relations (see Relation Extraction section). The build script 
> automatically extracts economic/inheritance relations as transactions in the output.
>
> **Relations with these attributes ARE transactions:**
> - `"sale"` — seller → buyer of property/goods
> - `"purchase"` — buyer receives from seller (inverse of sale)
> - `"mortgage"` — debtor pledges to creditor
> - `"debt"` — creditor-debtor relationship
> - `"inheritance"` — heir receives from deceased's estate
> - `"heir"` — specific inheritance/bequest recipient
>
> **Transaction data is embedded in relations:**
> ```json
> {
>   "from": "João",
>   "to": "Maria",
>   "attribute": "sale",          // ← This is the transaction type
>   "seller": "João",            // Transaction fields
>   "buyer": "Maria",
>   "value": "100 réis",
>   "property": "House on Main Street",  // Link to properties[] by description
>   "label": "venda de propriedade",
>   "date": "1850-05-15"
> }
> ```
>
> **Build script extraction:** The build automatically extracts the first economic/inheritance 
> relation from each document as the document-level `transaction` field in the output.

## Relation Extraction & Inference Marking - Language-Agnostic Rules (For Agent/GenAI)

### Core Fields for Every Relation

Every relation in `metadata/*.json` must include:

```json
{
  "from": "João",              // Source person name
  "to": "Maria",               // Target person name
  "relation": "vende a",       // Source language text (Portuguese, English, etc.)
  "attribute": "sale",         // English relation type (REQUIRED for build)
  "source": "explicit",        // Origin: explicit|inferred
  "inferedbyai": false,        // TRUE if agent inferred this (marked during OCR)
  "inference_type": "explicit", // explicit|inferred_same_doc|inferred_cross_doc
  "inference_confidence": "high" // high|medium|low (only if inferedbyai=true)
  // ... optional fields: seller, buyer, value, date, label, etc.
}
```

### Source Marking: When to Mark as Inferred

**`source: "explicit"`** - Directly stated in document text
```json
{
  "from": "João",
  "to": "Maria",
  "relation": "vende a",
  "attribute": "sale",
  "source": "explicit",
  "inferedbyai": false,
  "inference_type": "explicit",
  "inference_confidence": "high"
}
```

**`source: "inferred"` + `inferedbyai: true`** - Agent inferred during OCR
```json
{
  "from": "João",
  "to": "Filipa",
  "relation": "casado com",
  "attribute": "marriage",
  "source": "inferred",
  "inferedbyai": true,          // Agent marked this as inferred
  "inference_type": "inferred_same_doc",  // Inferred from document context
  "inference_confidence": "medium",        // Agent's assessment
  "inference_reasoning": "Document states 'João and his wife'; female name Filipa appears in family witness section. Inferred marriage based on context."
}
```

**`source: "inferred"` + `infered: true` (set by build script later)**
```
This is set by the build script when consolidating across documents with GLOSSARIO.
Agent does NOT set this field. Example: if GLOSSARIO links "João" (DL01) ↔ "João da Silva" (DL02),
the build script marks cross-document inferences as infered: true.
```

### Confidence Levels

When marking `inferedbyai: true`, assess confidence:

- **`high` (85%+):** Clear context, high certainty of inference
  - Example: Document says "João and his wife Maria were married in 1825" → marriage is explicit, confidence high
  - Example: "Mr João and his wife"; female name Maria appears in family section → inferred but likely, confidence high

- **`medium` (60-85%):** Some context, reasonable inference but not certain
  - Example: Document mentions "João" once, then "a mulher de João" (his wife) with no name given; someone named Filipa appears in will beneficiaries → could be wife but not certain, confidence medium

- **`low` (40-60%):** Weak context, speculative but worth recording
  - Example: João appears as seller in one section, Paulo appears as executor in another → could be related but not clear, confidence low

### Inference Types

- **`explicit`:** Directly stated in document (source: "explicit", inferedbyai: false)
- **`inferred_same_doc`:** Inferred from context within a single document (agent marks during OCR)
- **`inferred_cross_doc`:** Inferred by build script from GLOSSARIO linking persons across multiple documents (agent does NOT use this)

### Variant Grouping (In Persons Array)

When documenting person name variants:

```json
{
  "name": "João",
  "roles": ["seller", "testator"],
  "variants": [
    {
      "name": "João da Silva",
      "source": "document_context",   // Where variant found
      "confidence": "high",            // high|medium|low
      "reasoning": "Full name appears in property deed opening clause; clearly same person as 'João' in transaction list"
    },
    {
      "name": "João S.",
      "source": "signature_page",
      "confidence": "medium",
      "reasoning": "Abbreviated signature; likely same person but initials only"
    }
  ]
}
```

Do NOT force uniformity. Keep variants as found in document; GLOSSARIO.md will link them during build.

### Transaction Attributes (Optional, Type-Specific)

When a relation has transaction data, include relevant attributes:

```json
{
  "from": "João",
  "to": "Maria",
  "attribute": "sale",
  "label": "venda de propriedade",       // Transaction label extracted from document
  "seller": "João",                  // Transaction participant
  "buyer": "Maria",                     // Transaction participant
  "value": "100 réis",                // Transaction amount
  "date": "1850-05-15",                // Normalized date
  "date_precision": "day",              // day|month|year|approximate
  "date_original": "Fifteenth day of May" // Original text from transcript
}
```

Use only attributes relevant to the relation type (see table above).

### Date Normalization

Always normalize dates to YYYY-MM-DD format:

| Input | Output | date_precision | date_original |
|---|---|---|---|
| "15 May 1850" | "1850-05-15" | day | "15 May 1850" |
| "May 1850" | "1850-05-01" | month | "May 1850" |
| "1850" | "1850-01-01" | year | "1850" |
| "circa 1850" | "1850-01-01" | approximate | "circa 1850" |
| (no date) | (field omitted) | (field omitted) | (field omitted) |

Always preserve the original text in `date_original` for UI display.

### Agent Instructions: Extract `attribute` Field (REQUIRED)

**For each relation, extract TWO fields:**

1. **`relation`** - Keep the SOURCE LANGUAGE text (for display/label)
   - Example: "vende a", "filho de", "casado com" (Portuguese)
   - Example: "sells to", "son of", "married to" (English)
   - This is ONLY for human reading in tooltips/panels

2. **`attribute`** - Use ENGLISH relation type (language-agnostic)
   - Example: `"filiation"`, `"marriage"`, `"sale"`, `"purchase"`, `"mortgage"`
   - This MUST match one of the ~22 canonical relation types
   - **This field drives the build system** - build uses `attribute`, not `relation` text

### Why Language-Agnostic?

✅ **Build system does NOT parse relation text** - uses `attribute` field instead
✅ **Works with any document language** - Portuguese, Spanish, French, Latin, etc.
✅ **Future-proof** - no need to add language patterns to build script
✅ **Accurate** - GenAI/human decides category, not regex pattern matching
✅ **Clear semantics** - `relation` = display, `attribute` = classification

### Build Script Resolution Order

When determining the relation category, the build script checks in this order:

1. **`attribute` field** (if present) ← **USE THIS** (agent-extracted English type)
2. **`category` field** (if present) ← Fallback for pre-classified relations
3. **`_rel_cat()` parsing** (if neither above) ← Language-dependent, deprecated

**Recommendation:** Always extract `attribute` field to ensure language-agnostic processing.

### Person Fields (metadata/*.json)

**Required:**
- `name` - Canonical person name (string)
- `roles` - Array of roles (seller, testator, buyer, heir, witness, etc.)

**Optional:**
- `variants` - Array of variant names with source, confidence, reasoning
- `gender` - "F" or "M" (inferred from role/relation if missing)
- `birth`, `baptism`, `death` - Life event dates
- `profession` - Occupation (lavrador, escrivão, juiz, etc.)
- `birthplace`, `residence` - Locations
- `alias`, `notes` - Additional identifiers

### Symmetric Relations

Some relations are bidirectional and should be deduplicated:
- `marriage`: A married to B == B married to A (keep one)
- `kinship`: A brother of B == B brother of A (keep one)

Precedence when deduplicating: **explicit > glossary > inferred**

When there is a `filiation` (parent-child) and an inferred `descent` for the same pair, the build **removes** the `descent` (superseded by explicit filiation).

### Field Name Reference (English)

**Relation fields** (all required):
- `from`: Origin person name (string)
- `to`: Target person name (string)
- `relation`: Relation text (e.g., "son of", "sells to", "married to")
- `category`: Type enum (filiation|marriage|kinship|affinity|godparent|descent|inheritance|sale|purchase|mortgage|other)
- `source`: Origin marker ("explicit"|"glossary"|"inferred") - controls display style
- `source_images`: Array of image IDs where relation appears

**Optional relation fields**:
- `value`: Transaction amount (for sale/purchase/mortgage)
- `date`: Relation date (birth, marriage, transaction, etc.)
- `location`: Geographic location
- `status`: Processing notes (e.g., "widowed", "divorced")
- `notes`: Observation text
- `property`: Property ID (for property transactions)

**Person fields** (all required):
- `name`: Canonical person name (string)
- `variants`: Array of alternate name forms (strings)
- `source_images`: Array of image filenames where person appears

**Optional person fields**:
- `birth`: Birth date (YYYY-MM-DD or c. YYYY)
- `baptism`: Baptism date
- `death`: Death date or † marker
- `role`: Person's role in document (testator, buyer, seller, heir, godparent, etc.)
- `profession`: Occupation (lavrador, escrivão, juiz, etc.)
- `birthplace`: Birth location
- `residence`: Current residence
- `gender`: "F" or "M" (inferred from role/relation if missing)
- `alias`: Nickname or alternate name
- `burial`: Burial location
- `notes`: Person notes or observation text

## Local Knowledge from GLOSSARIO (`source:"glossary"`)

The `projects/<project>/GLOSSARIO.md` can contain a ```json``` block (section
*"Local Knowledge"*) with facts **not** in the OCR transcriptions
(the `metadata/*.json` files are immutable). The build reads it and merges it
into the consolidated `persons` and `relations` arrays with `source:"glossary"`..

### GLOSSARIO JSON Schema (English Field Names Required)

```json
{
  "identities": [ ["Canonical Name", "variant A", "variant B"] ],
  "persons":    [ {"name":"...","birth":"...","death":"...","role":"..."} ],
  "relations":  [ {"from":"...","relation":"son of","to":"...","source":"glossary"} ]
}
```

**IMPORTANT:** All field names MUST be English (not Portuguese):
- ✅ `identities`, `persons`, `relations`, `from`, `to`, `relation`, `source`
- ❌ NOT `identidades`, `pessoas`, `relacoes`, `de`, `para`, `relacao`, `fonte`

**Field definitions:**
- `identities`: Array of name groups. **First element = canonical**; rest are variants
  - Applied to: Both persons and relation endpoints
  - Example: `["Arlinda Maria", "Rolinda Maria", "Arlinda Maria Dias"]`
- `persons`: Array of person objects (same schema as top-level `persons[]`)
  - Fields: `name` (required), `birth`, `death`, `role`, `gender`, etc.
- `relations`: Array of relation objects (same schema as top-level `relations[]`)
  - Fields: `from`, `to`, `relation`, `attribute`, `source` (always "glossary")

**Build behavior:**
- Merges persons into aggregate top-level `persons[]` with `source:"glossary"` marker
- Merges relations into aggregate top-level `relations[]` with `source:"glossary"` marker
- Variants become `variants[]` field without forcing uniformity
- In viewer: relations with `source:"glossary"` use **attribute color** + **short dashing** (`2 4`))

## Discrepancies

Do not uniformize divergent readings (e.g., Rolinda/Arlinda, Galvão/Álvaro).
The build **discards conflicting glossary rules** (a term that is "wrong" in
one rule and "canonical" in another) to **preserve** those variants in
`variants`/`notes`.
